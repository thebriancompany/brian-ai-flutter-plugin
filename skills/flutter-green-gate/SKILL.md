# Flutter 품질 검사 반복

분석 → 포맷 → 테스트 → 커버리지를 실행하고 관찰한 실패만 수정한다. “CI를 통과시켜 줘”, “검사를 모두 통과할 때까지 수정해 줘”, 검사 계획·목표·범위 확인에 적용한다. 계획만 요청했다면 실행하지 않는다.

## 실행 기준

- 사용자와 저장소가 정한 도구·검사 기준·커버리지 목표를 우선한다. 별도 기준이 없으면 테스트 가능한 수작업 코드의 100%를 기본 목표로 제안한다.
- 사용 가능한 MCP는 실제 스키마를 확인해 쓴다. 없으면 CLI를 사용한다. 특정 호스트의 훅이나 도구 이름을 가정하지 않는다.
- 이전 성공을 최종 성공의 근거로 재사용하지 않는다. 수정 이후 같은 최종 검증 라운드에서 네 검사가 모두 통과해야 한다.
- 도구 실패·시간 초과·미실행을 검사 통과로 취급하지 않는다.
- 테스트 삭제·검증 약화·도달 가능한 코드 무시·무단 목표 하향으로 숫자를 맞추지 않는다. 사용자가 목표 변경을 명시하면 그 기준을 기록하고 적용한다.
- 테스트 작성은 [테스트 스킬](../flutter-testing/SKILL.md)을 따른다. 관련 없는 리팩터링은 피한다.

## 도구 선택

| 검사 | 연결된 MCP 예시 | CLI 대안 |
| --- | --- | --- |
| 분석 | Dart 서버의 analyze_files | `dart analyze` 또는 `flutter analyze` |
| 포맷 | Dart 서버의 dart_format | `dart format .`, 검증은 `dart format --output=none --set-exit-if-changed .` |
| 테스트·커버리지 | CLI 서버의 test | `very_good test --coverage --min-coverage <목표>` |

MCP의 roots는 스키마가 요구하는 file URI·경로 형식을 따른다. `applyFixes`는 승인된 수정 범위일 때만 사용한다. 테스트 도구가 지원하면 `coverage: true`, `min_coverage`, `check_ignore: true`, `exclude_coverage`, 대상 `directory`, 전체 실행 제한 `timeout_seconds`를 함께 확인한다. 셸 옵션을 MCP 필드처럼 섞지 않는다.

CLI의 ignore·exclude·재귀·제한 시간 옵션은 설치 버전의 도움말로 확인한다. `very_good`이 없으면 네이티브 테스트 러너와 별도 커버리지 검사를 사용할 수 있지만 네 검사의 의미를 모두 충족해야 한다. Flutter의 `flutter test --coverage`만 실행해 커버리지 기준까지 통과했다고 주장하지 않는다. 순수 Dart의 VM 커버리지는 필요한 수집·LCOV 변환 절차를 확인한다.

## 반복 절차

1. 대상 `pubspec.yaml`, 패키지 목록, 기준과 도구를 확인한다. 라운드·실패 목록·변경 파일을 기록한다.
2. 분석한다. 오류와 프로젝트 CI가 차단하는 경고를 해결한다. 이전부터 있던 범위 밖 진단은 구분해 보고한다.
3. 포맷한다. 바뀐 파일 수가 0인지 확인한다. 성공 종료만으로 포맷 검증을 통과했다고 판단하지 않는다.
4. 분석이 통과하면 테스트한다. 실패 테스트를 실제 기대 동작에 맞춰 수정한다.
5. 테스트 성공 후 이번 실행의 커버리지와 기준 검사 결과를 확인한다. 누락 파일·줄을 기준으로 테스트를 보완한다.
6. 변경이 있었다면 필요한 네 검사를 다시 실행한다. 최종 라운드에서 분석 통과·포맷 변경 0·테스트 통과·목표 커버리지 충족이 관찰되면 종료한다.

상위 검사가 실패하면 뒤의 결과를 신뢰하지 않는다. 컴파일 실패 후 오래된 LCOV를 읽지 않는다. 이미 모두 통과하는 패키지는 한 라운드로 끝낸다.

## 진행 상태

| 검사 | 기록 |
| --- | --- |
| 분석 | 정렬한 진단 코드·파일·줄 |
| 포맷 | 수정된 파일 집합 |
| 테스트 | 실패 테스트 이름·ID |
| 커버리지 | 측정값·누락 파일·누락 줄 수 |

패키지별 기본 수정 라운드는 5회다. 같은 실패가 반복되거나 두 검사 사이를 오가면 접근을 바꾸고 원인을 확인한다. 실패 수가 같다는 이유만으로 진전이 없다고 단정하지 않는다. 외부 도구 문제·제품 판단·실제 정체로 더 진행할 수 없으면 근거를 보고한다. 사용자에게 질문할 필요가 없는 코드 오류는 직접 해결한다.

## 커버리지

현재 실행의 기준 검사 결과가 통과 판정의 근거다. LCOV는 비율 표시와 누락 위치 확인에 사용하고 같은 제외 집합을 적용한다. 생성 코드(`*.g.dart`, `*.freezed.dart`, `*.gen.dart`, 생성 지역화 등)는 실제 생성 경로를 확인해 제외한다. 넓은 글로브로 수작업 코드를 숨기지 않는다. [상세 처리](references/coverage.md)를 참고한다.

## 멈출 때 보고할 내용

실패 검사·구체적 진단/테스트/파일, 변경 파일, 라운드 수, 도구 오류와 필요한 결정 하나를 제시한다. 숫자만 나열하지 않는다. 결정이 필요 없는 환경 제약은 해결 방법과 수행하지 못한 검사를 명시한다.

## 모노레포

대상 pubspec 목록을 명시하고 각 패키지에서 검사를 수행한다. 분석 대상과 테스트·커버리지 대상이 같아야 한다. 한 패키지 실패가 다른 패키지의 확인을 막지 않게 한다. 라운드 예산과 `<package>/coverage/lcov.info`를 패키지별로 관리하고 공유 목표인지 패키지별 목표인지 보고한다.
